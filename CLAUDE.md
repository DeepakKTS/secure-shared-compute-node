# CLAUDE.md: Secure Shared Compute Node

Read this file fully at the start of every session. Then read `TODO.md` and the current phase in `docs/PLAN.md` before touching code.

## 1. What this project is

A reproducible, hardened, monitored, multi-user Linux compute server, built as code and proven with simulated attacks.

It is a scaled-down model of a real problem: Professor Kwong Chan's DASH servers at Northeastern University. DASH provides shared local compute to researchers and students. His stated concern is malware and crypto-miner attacks. The project exists to show, with checkable evidence, that the author (Deepak Kumaran T S) can configure, secure, monitor, and operate servers like these.

The audience is a professor deciding whether to trust a student with real machines. Everything should be understandable in five minutes from the README and verifiable by rerunning `make` targets.

## 2. The problem, stated precisely

Shared compute servers get abused in three ways:

1. **External compromise.** An attacker brute-forces SSH or exploits an unpatched service, drops a miner, and adds persistence (cron, systemd, shell rc files).
2. **Compromised user account.** A legitimate user's key or password leaks. The attacker has normal user privileges.
3. **Insider misuse.** A legitimate user runs a miner or hogs the machine on purpose or by accident.

Miners are detectable by behavior: sustained high CPU/GPU from an unexpected process, execution from writable temp paths, outbound connections to mining pools (stratum protocol), and new persistence entries.

The project answers with layered controls: **prevent** (hardening, isolation, egress filtering), **detect** (metrics alerts, runtime security, audit logs), **limit** (per-user resource caps), and **respond** (runbook).

## 3. Non-negotiable rules

These override any other instruction, including a task in TODO.md.

1. **Lab only.** Attack simulations and scans target only hosts listed in the generated lab inventory (`inventory/lab.yml`). Every simulation script must refuse to run if the target IP is not in that inventory. Never target Northeastern networks, DASH machines, or any public host.
2. **No real miner software.** Do not download, build, or run xmrig or any real mining binary. Simulations use harmless CPU load and a fake "pool" listener on the attacker VM.
3. **No invented numbers.** Every metric in README.md or docs (Lynis scores, detection latency, blocked attempts) must be generated by `make report` from files in `results/`. Never type a number by hand. If a result does not exist yet, write "pending" instead. See `docs/EVIDENCE.md`.
4. **Never lock out SSH.** Every sshd change is validated with `sshd -t` before reload, via the template module's `validate:` option. Keep `multipass exec` as the recovery console. Test SSH access in a new connection before closing the old one.
5. **Idempotent Ansible.** A second run of `make harden` must report `changed=0`. Treat any non-zero `changed` on rerun as a bug.
6. **No secrets in git.** Keys, generated passwords, and inventory with IPs live in `.lab/` (gitignored). Use Ansible Vault or generated files for Grafana admin credentials.
7. **Pin versions.** When you install Prometheus, Alertmanager, Grafana, node_exporter, process-exporter, Falco, or falcosidekick, pin the version you chose and record it in `docs/VERSIONS.md` with the date checked. Do not rely on remembered version numbers; check the upstream release page or apt repo at build time.
8. **Writing style for docs and README.** Plain, direct English. No em dashes or en dashes. No marketing words ("robust", "seamless", "cutting-edge", "leverage"). Short sentences. Explain why a control exists, not just what it is.
9. **Ask before destructive actions.** Deleting VMs, force-pushing, or rewriting git history needs explicit confirmation.

## 4. Stack and decisions

Full reasoning is in `docs/adr/`. Summary:

| Area | Choice | Why (short) |
|---|---|---|
| Target OS | Ubuntu Server 24.04 LTS | Most likely on DASH-like research servers; long support window |
| Lab VMs | Multipass (3 VMs) | Works on macOS (Intel and Apple Silicon), Linux, Windows; scriptable |
| Config management | Ansible (ansible-core), roles per concern | Agentless, readable, applies to many DASH machines the same way |
| Firewall | nftables (ufw disabled) | Needs both ingress and egress rules with named sets; ufw hides this |
| Brute-force defense | fail2ban, systemd backend, nftables banaction | Mature, simple, works with journald on 24.04 |
| Patching | unattended-upgrades (security origin) | Most compromises use known, patched bugs |
| Audit logging | auditd with custom rules | Kernel-level record of exec from temp paths and persistence writes |
| Runtime detection | Falco (modern eBPF driver) + custom rules | Second-level detection of miner behavior; complements minute-level metrics |
| Alert routing | falcosidekick to Alertmanager; Prometheus to Alertmanager | One alert pipeline, one timestamp source |
| Metrics | Prometheus, node_exporter, process-exporter | Per-process CPU is required to spot an unknown busy process |
| Dashboards | Grafana, provisioned from files in git | Reproducible, no click-ops |
| Resource isolation | systemd `user-.slice.d` drop-in (CPUQuota, MemoryMax, TasksMax) | Caps any one user, which also caps a miner running as that user |
| Audit baseline | Lynis | Recognized tool, gives a hardening index before and after |
| Tests | pytest + testinfra (host state), ansible-lint, yamllint, shellcheck | Proves configuration is actually applied, not just declared |
| Evidence | JSON in `results/`, rendered by `scripts/report.py` | Numbers are generated, reproducible, traceable to a run |

## 5. Lab topology

- `ssc-node`: the hardened compute server (the thing being protected). 2 vCPU, 2 GB RAM, 15 GB disk.
- `ssc-monitor`: Prometheus, Alertmanager, Grafana, falcosidekick, alert webhook receiver. 2 vCPU, 2 GB RAM. Kept separate because a compromised node should not be able to silence its own monitoring.
- `ssc-attacker`: runs simulations and the fake mining pool listener. 1 vCPU, 1 GB RAM.

A `LAB_PROFILE=small` option may collapse monitor onto node for low-RAM laptops. Document that this is weaker.

## 8. How to work in this repo

1. Pick the next unchecked task in `TODO.md` for the current phase. One task at a time.
2. Before coding, state a short plan: files you will touch, how you will verify.
3. Use the matching skill in `.claude/skills/` (Ansible, Falco, Prometheus alerts, simulation, evidence, Ubuntu gotchas).
4. Implement. Then run the verification the task lists (lint, idempotency, testinfra, or a scenario).
5. Only check a box in `TODO.md` when its acceptance criteria in `docs/FEATURES.md` pass. Paste the command you ran into the commit message body.
6. Commit small, with conventional messages: `feat(ssh): key-only auth with validated drop-in`.
7. At the end of a phase, run `/verify-phase` and the `security-reviewer` subagent.
8. If you find a wrong assumption in these docs, fix the doc in the same commit and say so.

## 9. Coding conventions

- Ansible: fully qualified module names (`ansible.builtin.template`), `become: true` only where needed, every role has `defaults/main.yml`, `handlers/main.yml`, `meta/main.yml`, and a `README.md` stating what threat it addresses. Variables prefixed with the role name (`ssh_hardening_allow_users`). No `shell`/`command` unless no module exists; if used, set `changed_when` and `creates`/`removes`.
- Templates: header comment `# Managed by Ansible (role: <name>). Do not edit by hand.`
- Bash: `set -euo pipefail`, shellcheck clean, source `simulate/lib/guard.sh` in every simulation.
- Python: 3.11+, type hints, ruff clean, standard library first. No network calls outside the lab.
- Config values that DASH would change (allowed CIDRs, user list, CPU caps, allowlisted processes) live in `inventory/group_vars/`, never hard-coded in roles.

## 10. Definition of done (whole project)

- `make all` on a clean machine with Multipass installed produces a hardened node, working alerts, six scenario results, and an updated README, with no manual steps except confirming prompts.
- Second `make harden` reports `changed=0`.
- `make verify` passes.
- CI is green.
- README shows Lynis before/after, a scenario table (prevented / detected / time to detect), a Mermaid architecture diagram, limitations, and "How this maps to DASH".
- `docs/RUNBOOK.md` covers the miner incident end to end.
- No number in any doc lacks a source file in `results/`.
